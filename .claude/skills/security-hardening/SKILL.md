# CI・インフラ・外部通信の安全性

Claude、Codex、Geminiなどに共通の手順。特定エージェントのフックやツール名を前提にせず、対象リポジトリで使えるCLI・テスト環境を利用する。

## まず確認すること

- 入力元、認証情報を渡す相手、ログの出力先、本番権限を持つ処理をたどる。問題は「どの入力が、どの経路で、何を引き起こすか」で説明する。
- 依存パッケージは間接依存も監査する。最新の脆弱性情報・SDKの既定値・IAMのアクション別制限は、公式資料や既存の監査ツールで確認する。
- コード・設定の修正と、実環境への適用を区別する。依頼にない投稿、デプロイ、インフラ適用、権限変更は実行しない。

## 見落としやすい経路

| 対象 | 確認と対応 |
| --- | --- |
| CIのシェル | `run:` へ入力やsecretを直接埋め込まない。環境変数で受け、シェルでは引用した引数として渡す。文字列が実行コードにならないことを確認する |
| ビルドと本番権限 | ビルドは依存パッケージやリポジトリ内スクリプトも実行する。OIDC発行権限・本番認証情報を持つジョブから分離し、同じ実行で作った成果物だけを受け渡す |
| GitHub Actions | 不要なトークン権限とcheckout後の認証情報の保存を避ける。外部アクションはSHA固定し、手動実行時のブランチ条件も確認する |
| IAMの信頼 | アカウントrootのARNはrootユーザー限定ではない。指定ユーザー／ロールを信頼ポリシー側でも限定し、別の広いAssumeRole権限から入れないか確認する |
| IAMの権限 | `PassRole` は渡してよいロールとサービスを限定する。リソース名末尾の `*` が同じ接頭辞の別リソースに広がらないか確認する。リソース指定不能な一覧APIは別ステートメントにする |
| 自己権限変更 | 自分のIAMポリシーを編集できる主体には、通常の許可ポリシーだけで上限を作れない。権限境界やSCPを別の管理主体で管理する必要性を説明し、制約を勝手に外さない |
| APIの転送・容量 | 認証付き通信の自動転送で独自ヘッダーが漏れないか確認する。転送先が固定なら自動転送を禁止し、タイムアウトと応答サイズの上限を設ける |
| エラーとログ | 外部応答の全文・認証ヘッダー・環境変数の値を出さない。内部例外にも応答の断片が入ることがある。調査に必要な操作名・状態コードなど、許可した項目だけを残す |
| 数値・構造 | 不正入力による桁あふれ、欠落、重複、不完全な集合を確認する。暗黙の補完や部分的な成功で誤った結果を出さない |
| 再試行と副作用 | アプリだけでなくSDK・ジョブ基盤・イベント配信側の再試行も確認する。応答喪失は未処理の証拠にはならない。投稿・課金等は再実行の抑止か冪等性を設計し、重複配信との違いを明記する |

SHA-1等の名前だけで危険と決めつけない。外部プロトコルが指定する署名方式を独自に変更すると認証が壊れるため、用途と仕様を確認する。

## 検証と仕上げ

- 外部投稿はスタブへ置換する。HTTPハンドラ自体の挙動はループバック等の閉じた環境で検証する。Terraformのテストは全providerをモック化し、`command = plan` とする。
- 安全性のテストでは「転送先へ送信されない」「ログに秘密情報が出ない」「許可対象が広がらない」などの結果を検証する。テスト用の値は本物の認証情報から作らない。
- 実データを使う必要がある場合も、秘密ファイルを表示・sourceせず、必要な値だけをメモリ内で読み取る。認証先を限定し、応答と例外は公開前に確認する。
- 機密情報スキャンはredactを有効にする。ローカルの秘密ファイルを含む作業ツリー全体の結果を、そのままログやPRへ貼らない。
- 変更を検証してから報告する。確認できた範囲、実環境では未検証の点、残る管理者権限や運用上の制約を区別する。skillへの追記は再利用できる判断基準に絞り、個別の設定値はリポジトリの開発ガイドへ置く。
