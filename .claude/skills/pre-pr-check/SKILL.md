# PR前の最終確認

変更をコミット・PRにする前に、以下を順に行う。目的は「レビュアーがCIの失敗や機密漏れの指摘に時間を使わず、変更の中身のレビューに集中できる状態」でPRを出すこと。

## 1. ブランチと差分の範囲を確認する

- デフォルトブランチ（master/main）上で作業していないことを確認する。乗っていたら先にブランチを切る。
- `git status` と `git diff --stat` で、意図しないファイル（ビルド成果物・ローカル設定・一時ファイル）が混ざっていないかを見る。

## 2. プロジェクトの検証コマンドを実行する

CLAUDE.md や README に書かれたビルド・フォーマット・テストのコマンドをそのまま使う（CIと同じ検証をローカルで済ませる）。書かれていなければ、リポジトリの種類から判断する（.sln → `dotnet build/format/test`、package.json → `npm run lint/test`、pyproject → `ruff`/`pytest` など）。フォーマッタは「検証」ではなく「適用」で実行し、直った差分ごとコミットに含める。失敗はすべて直してから先へ進む。直せない場合は、その事実と理由をPR本文に書く。

## 3. 機密情報・環境固有値をスキャンする

検出は既存ツールに任せる（自前のパターン集を書かない）。未導入なら `brew install gitleaks`。

```bash
gitleaks git --no-banner --redact --log-opts="<base>..HEAD"   # コミット済みの差分（base はデフォルトブランチ）
gitleaks git --no-banner --redact --pre-commit                  # 未ステージの変更
gitleaks git --no-banner --redact --staged                      # ステージ済みの変更
gitleaks dir --no-banner --redact <確認用ディレクトリ>          # Git管理対象・追加予定ファイルだけをコピーして検査
git secrets --scan                                     # git-secrets を導入済みのリポジトリでは併用（pre-commitフックと同じ検査）
```

秘密ファイルの値を画面・コマンド引数・PRへ出さない。gitignore対象の `.env` やstateを確認用コピーに含めない。git-secretsなどredact機能のないツールの出力は捕捉し、検出行をそのまま表示しない。失敗時も値を伏せたまま該当箇所を調べる。

認証情報・IAM・外部入力を変更した場合は、利用可能なら `security-hardening` skillも参照し、転送・ログ・シェル・権限を通じた流出や権限拡大を確認する。

テストの固定入力（ダミー鍵から計算した署名値など）を高エントロピー文字列として誤検出することがある。機密でないと確認できたら、その行に `// gitleaks:allow` を理由のコメントとともに付けて除外する（`.gitleaksignore` や設定ファイルではなく行に書くと、値が変わったときに指定が自然に無効になる）。

gitleaks はAPIキー・トークン・秘密鍵を対象にしており、「機密ではないが環境固有の値」は検出しない。それらは追加行に対する grep で拾う（AWSアカウントID・ARN・バケット名・リソースURL・メールアドレス・内部IP）:

```bash
git diff <base>...HEAD | grep -nE '^\+' | grep -iE 'arn:aws|amazonaws\.com|s3://|[^0-9][0-9]{12}[^0-9]|[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[a-z]{2,}|([0-9]{1,3}\.){3}[0-9]{1,3}'
```

検出されたら1件ずつ判断する:

- 実値（本物のキー・アカウントID・バケット名・ARN・個人メールなど）→ 削除し、環境変数や gitignore 対象の設定ファイルへ移す。既にコミット済みなら、そのコミットを作り直す（履歴に残った時点で漏洩扱い）。
- ダミー値（`.example` ファイル、テストの固定入力、ドキュメントの例）→ 「書き換えないと必ずエラーになる明らかなダミー」であることを確認して通す。実値に似せたダミーは避ける。

## 4. ドキュメント・コメントの追随を確認する

変更で名前が変わった／消えたもの（クラス・メソッド・環境変数・コマンド・ファイル・設定キー）を `grep -rn` でドキュメント（README, CLAUDE.md, docs/）とコード内コメントから探し、古い記述を直す。ドキュメントに「具体例の複製」を増やさない（フォーマットが変わるたびに直す場所を増やさない）。

## 5. 結果を報告してからコミット・PRへ進む

以下を簡潔に報告し、問題がなければコミット・PR作成に進む。PRテンプレート（`.github/pull_request_template.md`）があればその構成に沿って本文を書く。テンプレートが動作確認の出力（ドライラン結果など）を求めていれば、実際に実行した出力を貼る。実行できなかった場合は「未実施」と理由を明記し、実施したように書かない。

- 実行した検証コマンドと結果（すべて成功／失敗内容）
- スキャンの検出件数と、それぞれをどう判断したか
- 追随修正したドキュメント・コメント
