# 仕様ベースのテスト

## 狙い

テストは「仕様が守られているか」を検証するもので、「今の実装がこう書かれているか」を写し取るものではない。実装の詳細に依存したテストは、振る舞いを変えないリファクタや文面の微調整のたびに壊れ、直す作業が「テストを今の実装に合わせ直す」だけの空作業になる。そうなるとテストは変更の安全網ではなく変更の抵抗になる。書く前に「この実装を別のやり方に書き換えても、このテストは通るべきか？」を自問し、通るべきならそのテストが実装の書き換えで壊れない形になっているかを確かめる。

## 依存させないもの（変わりやすいもの）

| 依存させないもの | 代わりに検証すること |
|---|---|
| 出力文字列の全文・レイアウト（改行位置・区切り文字・装飾） | 「データが出力に含まれる」「順序が正しい」「上限を超えない」という入出力の関係 |
| 具体的な例外の型・メッセージ文言 | 「失敗する」こと（`ThrowsAny<Exception>`）。型を検証するのは、呼び出し側がその型で分岐している場合だけ |
| 毎シーズン・毎年変わる実データの中身（マスタの値、日付、外部APIの応答） | 実データを使わず固定入力を注入する。実データに対しては「網羅性」など安定した不変条件だけを検証する |
| 内部のprivateメソッド・中間表現・呼び出し回数 | 公開された入口からの結果。内部を直接テストしたくなるのは責務の切り出しが必要なサイン |
| ログ出力の文言 | 検証しない（ログは仕様ではなく運用の道具。必要なら「エラーになる／ならない」で検証する） |

## 書き方のパターン

- **変わりやすいデータは注入できるようにする**: マスタ（例: タグ対応表）を受け取るコンストラクタを用意し、テストでは最小限のダミーを渡す。本物のマスタを使うテストは「全項目が定義されている」など網羅性の検証1本に絞る。定期更新が本体1ファイルで済み、テストの追随修正が要らない構造になる。
- **「考慮漏れを検出する」テストは、完全な集合を1か所で定義する**: 例えば全チーム名の配列をテストに1つ持ち、マスタのキー集合と一致することを検証する。個別のエントリを1つずつ検証しない。
- **境界値と同値クラス**: 上限ちょうど／1超過、期間の開始日／前日、空入力、要素1件。仕様の境界は実装が変わっても動かないので、テストとして長持ちする。
- **1テスト1事実**: テスト名が仕様文になるように書く（例: `上限ちょうどは超過ではない`）。複数の仕様を1つのテストに詰めると、失敗時にどの仕様が破れたかわからず、変更の影響範囲も読めない。
- **フェイクは振る舞いだけを持つ**: インターフェースの手書きフェイク（結果を返す／例外を投げる／呼び出しを記録する）で十分なことが多い。モックライブラリで呼び出し順や回数まで縛ると実装依存になりやすい。
- **時刻・乱数・外部I/Oは引数や差し替え可能な依存にする**: 純粋関数にできれば固定入力でどの境界も検証できる。

## 既存テストを見直すときのチェック

1. 出力の全文一致（`Assert.Equal(期待文字列全体, 出力)`）になっていないか → 含まれる／順序／件数に分解する
2. 実データ（本番マスタ・実際の日付）に期待値が結びついていないか → 注入に切り替える
3. 実装の書き換え（アルゴリズム変更・クラス分割）で壊れるテストがないか → 公開入口経由に寄せる
4. 同じ仕様を複数のテストが重複して検証していないか → 独立に導出した期待値を持つ1本に統合する
5. テストのために `internal` 公開や専用コンストラクタが増えていないか → 増やすなら「注入のため」に限る

## 例外的に実装寄りの検証をしてよい場合

- 外部仕様に対する固定入力・固定期待値（例: RFCどおりに独立計算した署名値、公開APIの実レスポンス抜粋の解析）。期待値が実装ではなく外部仕様から導かれているなら、それは仕様テストである。
- 回帰の再発防止で、特定の組み合わせが上限を超えないことなど、実データでしか検出できないもの。その場合はテスト内に「なぜ実データを使うか」を書き、それ以外のテストが実データに依存しない状態を保つ。
